## Special setup requirements — read this first

- **GPU is required.** The proposed neural models (Gated Pooling / SkuTemporalCNN, DeepSets, Set Transformer) are PyTorch models trained on GPU. An NVIDIA GPU with a CUDA-enabled PyTorch build is required to re-run the main experiments. The external benchmark models (sklearn) are CPU-only.
- **Disk space.** Regenerating the preprocessed sample cache for the 100% runs needs roughly 105 GB (25 GB holdout + 80 GB rolling). The caches regenerate quickly from the raw data (about 8 minutes each on the 208-core instance — see Flow A step 2).
- **RAM.** Building the cache constructs a dense item–store panel (about 59 million rows × 26 features) plus per-task tensors in memory. The original runs used an AutoDL GPU instance (Ubuntu 22.04, NVIDIA RTX 4090 48 GB, Intel Xeon Platinum 8470Q (25 cores), 92 GB RAM).
- **Long runs.** Run experiments inside `tmux`/`screen` over SSH so they survive disconnects.
- **Thread limiting.** Set these before every run to avoid CPU oversubscription:

  ```bash
  export PYTHONUNBUFFERED=1
  export OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 NUMEXPR_NUM_THREADS=1
  ```

- **Hyperparameter selection is not part of the reproduction flow.** The proposed models were originally tuned with a two-stage Optuna search, but tuning is stochastic: re-running it samples different configurations and can land on different hyperparameters, so the downstream results would not reproduce exactly. The reproduction flows below therefore use the frozen, pre-selected hyperparameters shipped in `results/work/*/01_tuning/` — the exact configurations that produced the paper's numbers (paper Tables 8–9 document the search ranges and the selected configurations). If you want to re-run the tuning yourself, see "Hyperparameter tuning (optional)".

## Data

The experiments use the **M5 forecasting competition dataset** (Makridakis et al., 2022; Kaggle "M5 Forecasting - Accuracy", https://www.kaggle.com/competitions/m5-forecasting-accuracy). It is public and freely available after a free Kaggle registration.

- **Files included in `data/m5/`:** `sales_train_evaluation.csv` (main file, 3,049 products × 1,941 days), `calendar.csv` (dates, SNAP and event flags), `sell_prices.csv` (weekly SKU–store prices), `sales_train_validation.csv` (fallback if the evaluation file is absent).
- **Preprocessing pipeline** (`code/scripts/prepare_m5_experiments.py`): the wide sales table is melted into a long item–store panel; calendar features (weekday, month, year, SNAP, events) and price features (sell price, price-change ratio) are merged; a store-SKU sample is drawn with `--store-sku-sample-frac` and seed 42; aggregate units are formed per task (`store_dept`, `store_cat`, `state_dept`); and dense per-aggregate samples are cached (cache version `v5_child_targets_bottomup_global_boosting`).

## Reproduction flows

Paths below assume you are in `code/` with `data/` and `results/` from this package alongside, on a Linux machine with the conda environment activated.

**Exactness note.** Regenerating the tables and figures from the shipped intermediary results (Flow C alone) reproduces the paper's values exactly — all tables were verified value-identical (checked 2026-10-04; paper Table 11 was updated on 2026-10-06 to the package's regenerated values). A full re-run from the raw data (Flow A) may, however, produce slightly different numbers: GPU training is not bit-deterministic, and results can shift a little across hardware and library versions (the per-fold WSPL differences that paper Table 11 previously showed were of order 1%). Such differences do not change the paper's conclusions — the model rankings, the statistical test outcomes and all qualitative findings are robust to them. Compare your fresh outputs with the paper at the level of findings, not last-digit equality.

### Flow A — Full reproduction: build the caches, run all experiments, generate the paper's tables and figures

This flow regenerates everything from the raw data. The experiment work dirs use the same paths as the shipped pre-generated results (`../results/work/...`), so the runs overwrite those directories in place — the frozen hyperparameters in their `01_tuning/` folders are already there, and Flow C afterwards runs exactly as written with no path substitutions. Keep the package zip as the pristine baseline if you want to compare against the shipped values afterwards.

1. Set the environment (see "Special setup requirements") and make sure the raw M5 data is in `../data/m5/`.

2. Build the sample caches (about 8 minutes each on the 208-core AutoDL instance; ~2 h holdout / several hours rolling on the original 25-core machine):

   ```bash
   # 100% holdout cache (~25 GB)
   python scripts/warm_m5_cache.py --data-dir ../data/m5 --cache-dir cache/100pct \
     --tasks store_dept,store_cat,state_dept --holdout \
     --t-hist 56 --horizon 28 --valid-size 4 --test-size 4 --internal-valid-size 3 \
     --store-sku-sample-frac 1.0 --store-sku-sample-seed 42
   # 100% rolling cache (holdout + rolling folds; ~80 GB)
   python scripts/warm_m5_cache.py --data-dir ../data/m5 --cache-dir cache/100pct_rolling \
     --tasks store_dept,store_cat,state_dept --holdout --rolling \
     --t-hist 56 --horizon 28 --valid-size 4 --test-size 4 --internal-valid-size 3 \
     --store-sku-sample-frac 1.0 --store-sku-sample-seed 42
   # Robustness fractions (holdout only)
   for FRAC_DIR in 10pct 30pct 50pct; do
     FRAC=0.${FRAC_DIR%pct}
     python scripts/warm_m5_cache.py --data-dir ../data/m5 --cache-dir cache/$FRAC_DIR \
       --tasks store_dept,store_cat,state_dept --holdout \
       --t-hist 56 --horizon 28 --valid-size 4 --test-size 4 --internal-valid-size 3 \
       --store-sku-sample-frac $FRAC --store-sku-sample-seed 42
   done
   ```

3. Main holdout run (writes into `../results/work/100pct/`; the frozen hyperparameters in `01_tuning/` are used as-is):

   ```bash
   python scripts/run_paper_experiment_plan.py \
     --data-dir ../data/m5 --work-dir ../results/work/100pct --cache-dir cache/100pct \
     --mode holdout --tasks store_dept,store_cat,state_dept \
     --proposed-models M3_FullSkuTemporalCNN,DeepSets,SetTransformer \
     --ablation-params-model M3_FullSkuTemporalCNN \
     --phases ablation,benchmark,stats,tables \
     --t-hist 56 --horizon 28 --valid-size 4 --test-size 4 --internal-valid-size 3 \
     --store-sku-sample-frac 1.0 --store-sku-sample-seed 42 \
     --final-epochs 24 --final-patience 6 --stats-metric wspl
   ```

4. Main rolling run: same command with `--mode rolling --work-dir ../results/work/100pct_rolling --cache-dir cache/100pct_rolling`.

5. Robustness fractions (holdout at each fraction, writing into `../results/work/<frac>/`):

   ```bash
   for FRAC_DIR in 10pct 30pct 50pct; do
     FRAC=0.${FRAC_DIR%pct}
     python scripts/run_paper_experiment_plan.py \
       --data-dir ../data/m5 --work-dir ../results/work/$FRAC_DIR --cache-dir cache/$FRAC_DIR \
       --mode holdout --tasks store_dept,store_cat,state_dept \
       --proposed-models M3_FullSkuTemporalCNN,DeepSets,SetTransformer \
       --ablation-params-model M3_FullSkuTemporalCNN \
       --phases ablation,benchmark,stats,tables \
       --t-hist 56 --horizon 28 --valid-size 4 --test-size 4 --internal-valid-size 3 \
       --store-sku-sample-frac $FRAC --store-sku-sample-seed 42 \
       --final-epochs 24 --final-patience 6 --stats-metric wspl
   done
   ```

6. Consistency checks:

   ```bash
   python scripts/check_experiment_consistency.py --work-dir ../results/work/100pct --mode holdout --metric wspl
   python scripts/check_experiment_consistency.py --work-dir ../results/work/100pct_rolling --mode rolling --metric wspl
   ```

7. Generate the paper's tables and figures: run Flow C exactly as written — its paths point at `../results/work/...`, which now hold your fresh outputs — and finish with Flow C step 9 to compare against the paper's inline values.

Validation notes: step 2 was executed and validated on 2026-10-04 (Python 3.12, pandas 3.0; the rebuilt caches match the shipped ones essentially byte-for-byte). A holdout run of steps 3 and 6 was started on the same instance and the ablation, benchmark and proposed-model phases all completed without errors before the run was stopped (~1.8 days of GPU time on the RTX 4090); the shipped `run_all.log` files record the original machine's complete runs.

### Flow C — Regenerate every paper table and figure from the intermediary results (no retraining)

Every downstream step (statistical tests, paper tables, CD diagrams) is a fast CPU-only script that consumes the shipped phase outputs in `results/work/` — no training, no GPU, a few minutes in total. Run everything from within `code/` with the conda environment activated.

**Prerequisite (layout).** Three helper scripts (`generate_cd_diagrams_100pct.py`, `build_rolling_fold_tables.py`, `build_robustness_tables.py`) hard-code the original repository layout and expect `results/work` next to `scripts/`. Point them at the shipped results with a symlink — Linux: `ln -s ../results results`; Windows: `mklink /J results ..\results` — so `code/results/work` resolves to the package's `results/work`.

**1. Statistical tests and CD diagrams for the holdout results (backing paper Tables 1–2 and Figures 2–3).** Run the Friedman/Nemenyi test per metric; it writes the stat CSVs/TeX and an untagged CD PNG into the output dir:

```bash
for METRIC in wrmsse wspl; do
  python scripts/run_m5_stat_tests.py \
    --benchmark-rows ../results/work/100pct/03_benchmark_baselines/all_holdout_rows.csv \
    --benchmark-series-rows ../results/work/100pct/03_benchmark_baselines/all_holdout_series_rows.csv \
    --proposed-rows ../results/work/100pct/04_benchmark_proposed/proposed_all_holdout_rows.csv \
    --proposed-series-rows ../results/work/100pct/04_benchmark_proposed/proposed_all_holdout_series_rows.csv \
    --ablation-rows ../results/work/100pct/02_ablation/all_ablation_rows_holdout.csv \
    --ablation-series-rows ../results/work/100pct/02_ablation/all_ablation_series_rows_holdout.csv \
    --ablation-models M0_AggHistOnly,M1_AggHistFutureSummary \
    --metric $METRIC --analysis-level series --series-block-cols task,agg_id \
    --output-dir generated/05_stat_tests_holdout
done
```

Then generate the paper-consistent CD diagrams. Figures 2–3 (holdout) come from the series-level script; Figures 4–5 (rolling) come from the fold-level script — the paper's rolling figures use 605 fold-level blocks (121 aggregate series × 5 rolling folds):

```bash
python scripts/generate_cd_diagrams_100pct.py
python scripts/generate_cd_diagrams_100pct_rolling_foldlevel.py
```

Both read the shipped series rows from `results/work/100pct` and `results/work/100pct_rolling` (via the `results` symlink), write their stat tables into the work dirs' `05_stat_tests/` folders, and write the PNGs into `results/work/figures/` (in place): `Figure_cd_diagram_*_series_holdout.png` (Figures 2–3) and `Figure_cd_diagram_*_series_rolling_foldlevel.png` (Figures 4–5). The first script also writes supplementary series-level rolling diagrams (`_rolling` suffix, 121 blocks); the paper uses the fold-level versions. The regenerated statistics are identical to the paper's; the PNG rendering may differ cosmetically with a different matplotlib version.

**2. Paper Tables 1–2 (plus the standalone ablation table).** Merge the shipped benchmark, proposed and ablation rows into paper tables:

```bash
python scripts/make_m5_paper_tables.py \
  --benchmark-rows ../results/work/100pct/03_benchmark_baselines/all_holdout_rows.csv \
  --proposed-rows ../results/work/100pct/04_benchmark_proposed/proposed_all_holdout_rows.csv \

  --output-dir generated/06_paper_tables_holdout
```

This writes `Table2_main_point.tex` (paper Table 1), `Table3_main_quantile.tex` (paper Table 2) and `Table4_ablation.tex`. Compare with the shipped versions in `results/work/100pct/06_paper_tables/`.

**3. Paper Tables 3–4 (rolling origin).** Same command with the rolling rows:

```bash
python scripts/make_m5_paper_tables.py \
  --benchmark-rows ../results/work/100pct_rolling/03_benchmark_baselines/all_rolling_rows.csv \
  --proposed-rows ../results/work/100pct_rolling/04_benchmark_proposed/proposed_all_rolling_rows.csv \
  --ablation-rows ../results/work/100pct_rolling/02_ablation/all_ablation_rows_rolling.csv \
```

**4. Paper Tables 10–11 (per-origin rolling appendix).**

```bash
mkdir -p generated && cd generated && python ../scripts/build_rolling_fold_tables.py && cd ..
```

It writes `appendix_rolling_folds_point.tex` and `appendix_rolling_folds_quantile.tex` into the current directory — compare with the copies shipped in `code/`.

**5. Paper Tables 5–6 and 12–13 (sample-fraction robustness).** Regenerate the per-fraction tables from the 30% and 50% work dirs (the 100% holdout table was produced in step 2):

```bash
for FRAC in 30pct 50pct; do
  python scripts/make_m5_paper_tables.py \
```

## Hyperparameter tuning (optional)

The reproduction flows above deliberately skip hyperparameter selection. The reason is reproducibility: the Optuna search is stochastic, so re-running it produces different hyperparameters on every run — and with them, slightly different results. For the paper, the search was run once and its outcome (the selected configurations in `results/work/100pct/01_tuning/<model>/best_params.json`) was frozen for all downstream experiments, which is what Flow A reproduces.

If you want to explore the tuning process itself:

1. Make sure the cache for the target fraction exists (see Flow A step 2).
2. Run the tuner once per model. Example for the 100% SKU sample, matching the paper's procedure (the search is warm-started from the 50% tuning result, and `full100` narrows the search ranges for the full sample):

```bash
for MODEL in M3_FullSkuTemporalCNN DeepSets SetTransformer; do
  python scripts/tune_m5_proposed_models.py \
    --data-dir ../data/m5 --cache-dir cache/100pct \
    --output-dir work/tuning_100pct/${MODEL} \
    --mode holdout --tasks store_dept,store_cat,state_dept \
    --model-name "$MODEL" --search-profile full100 \
    --warm-start-params ../results/work/50pct/01_tuning/${MODEL}/best_params.json \
    --t-hist 56 --horizon 28 --valid-size 4 --test-size 4 --internal-valid-size 3 \
    --store-sku-sample-frac 1.0 --store-sku-sample-seed 42 \
    --stage1-n-trials 100 --stage1-train-frac 0.30 --stage1-epochs 8 --stage1-patience 3 \
    --stage2-top-k 10 --stage2-train-frac 0.80 --stage2-epochs 16 --stage2-patience 5 \
    --final-epochs 32 --final-patience 8 \
    --storage "sqlite:///work/tuning_100pct/optuna_${MODEL}.db"
done
```

How it works (as described in the paper): the models are tuned with Optuna (Akiba et al., 2019) through a two-stage search followed by final retraining. Stage 1 performs a broad search with 100 trials; each configuration is trained for at most 8 epochs with an early-stopping patience of 3 (out-of-memory trials are pruned, not retried). Stage 2 re-evaluates the 10 best Stage 1 configurations with a maximum of 16 epochs and patience of 5, retrying OOM trials with smaller batch sizes. The configuration with the best Stage 2 validation performance is then selected for final retraining for up to 32 epochs with patience of 8. The tuning objective is the mean validation WRMSSE for point forecasting. The `--storage` flag persists the Optuna study so an interrupted search can be resumed.

The search space of the `full100` profile — the one used for the main 100% run above — is exactly the search-ranges table reported in the paper (paper Table 8):

| Hyperparameter | Gated Pooling / DeepSets | Set Transformer |
|---|---|---|
| Learning rate (log scale) | $[1\times10^{-4},\,5\times10^{-4}]$ | $[1\times10^{-4},\,5\times10^{-4}]$ |
| Dropout | $[0.01,\,0.08]$ | $[0.01,\,0.08]$ |
| Weight decay (log scale) | $[1\times10^{-6},\,1\times10^{-4}]$ | $[1\times10^{-6},\,1\times10^{-4}]$ |
| Hidden dimension | $\{64,96,128\}$ | $\{96,128\}$ |
| Batch size | $\{4,8,16\}$ | $\{4,8\}$ |
| CNN blocks | $\{2,3\}$ | $\{2,3\}$ |
| CNN kernel size | $\{3,5\}$ | $\{3,5\}$ |
| Attention heads | --- | $\{2,4\}$ |
| ISAB layers | --- | $\{1,2\}$ |
| Inducing points | --- | $\{16,32\}$ |

For other SKU fractions use `--search-profile auto`, which maps the fraction to the right profile (`sample10` for 0.10, `large30` for 0.30, `large50` for 0.50, `full100` for 1.00); the smaller-fraction profiles use wider variants of these ranges.

The tuned parameters are written to `<output-dir>/best_params.json` (the search space and stage summaries go into `tuning_run_config.json` and the CSV logs). To use your own tuned parameters in the downstream experiments, copy them into `work/<mode>/01_tuning/<model>/best_params.json` — the location the orchestrator reads — and run the `ablation,benchmark,stats,tables` phases exactly as in Flow A. Expect your results to differ slightly from the paper's, since your tuned configuration will differ from the frozen one.

Tuning cost: the paper's 100% search was warm-started from the 50% result (so Stage 1 ran fewer trials) and took about three GPU-hours in total across the three models on the original machine (see the tuning section of `results/work/100pct/run_all.log`); a cold run of the full 100-trial Stage 1 takes proportionally longer.
